## What it is

RACI assigns four roles to every activity a business performs. *Responsible* does the work.
*Accountable* owns the outcome, and there is exactly one, and it is a named person. *Consulted*
is asked before the decision. *Informed* is told after it.

Most of the model's value sits in the distance between the first two letters. Responsible is
about hands; accountable is about consequences. Merge them and you get the two familiar
failures: work that everybody is doing and nobody owns, or work that one owner is personally
performing because delegating it felt like losing control of it.

The letters matter more now than they used to, because R is the letter that can be delegated to
a machine. An agent can gather, draft, reconcile, schedule and file. It cannot be accountable —
not for legal reasons and not for sentimental ones, but because accountability means someone
can be asked to explain the decision and made to live with it, and that is a property of
people. So the model splits cleanly in an agentic organisation: R is a capability question, A
is a judgement question, and the line between them is where a routing diagram has to stop and
wait for a human.

## When to run it, and when not

Run it after there is something worth routing: activities from the model, actions from a
constraint diagnosis, objectives with owners. Run it when work visibly stalls and nobody in the
building can say whose desk it is sitting on. Run it before delegating anything to an agent —
before, because the boundaries are much harder to write once something is already running.

Run it on activities, not on people. RACI is a routing table for work; an org chart is a map of
reporting lines. Treating the second as the first is how you end up with a matrix that
describes rank instead of flow.

Do not run it to spread accountability. Two names in the A column is not caution, it is an
unassigned outcome with extra steps. Do not run it as a compliance exercise for a project that
has already started, and do not run it once. A routing table is only true as long as the work
and the constraint stay where they were.

## How it became wallpaper

The matrix is built at the kickoff, and consulted approximately never after it.

The session itself goes well. Thirty rows, everyone in the room, a lively argument about two of
them and easy agreement on the rest. The grid is filled in, colour-coded, exported and saved to
the shared drive, and everybody leaves with the pleasant feeling of a thing having been
settled.

Six weeks later a change order lands, and nobody opens the file. They walk to whoever's desk is
nearest, or they message the person who answered last time. Not out of laziness — out of speed.
The matrix described the project as it was imagined at the start, and the work in front of them
is the project as it actually arrived: a scope change nobody anticipated, a customer date that
was not in the plan, three crews who need an answer this afternoon.

The A column is where the damage compounds. In the room, accountability drifts upward, because
assigning it to the most senior person present feels like rigour and costs nothing at the time.
So one desk ends up owning every decision on the critical path. It does not read as a problem
in the grid — a matrix with one name repeated down a column looks tidy. It reads as a problem
in the schedule, weeks later, as a queue in front of a person who is doing their best.

> A matrix nobody opens is not a routing table. It is an opinion about who should have been asked.

## What good looks like

**One accountable name per activity, and it is a person.** Not a team, not a committee, not a
role that three people share. If naming the person is politically hard, that difficulty is the
finding, and it will not become easier once the work is late.

**Responsible is asked as a capability question.** Can this step be done by an agent, given
clear inputs and a checkable output? Plenty of steps can — intake, reconciliation, drafting,
re-sequencing a schedule against fixed rules. Deciding that honestly is worth more than a policy
about automation in either direction.

**Every delegation ships with its boundaries.** Which systems the work may touch, which data it
may see, what it may commit or spend, the threshold above which it stops and asks, and how the
delegation is revoked. Boundaries written at the same time as the assignment are a design;
boundaries written afterwards are an incident report.

**The stops are designed.** A packet that pauses for a human signature is not a failure of
automation, it is the system working — but the pause should be where the judgement is, its
holder should be named, and the wait should be measured. An approval queue nobody times is a
constraint nobody has noticed.

**It is re-routed when the constraint moves.** The right routing table for a business limited by
delivery capacity is not the right one for a business limited by demand. When the limit moves,
the assignments that protected the old one quietly start protecting nothing.
